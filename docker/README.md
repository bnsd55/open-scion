# A scion demo under Docker

One image carries `scion-server`, `scion-cache`, and `scn`. The demo brings
up a server and a cache, both with TLS, seeds a repo with one commit, and
checks it out through the cache.

```sh
sh docker/demo.sh
```

What it does:

1. Makes the demo secrets at compose time: one CA, a certificate for each
   of `server` and `cache`, and the server's ticket key (made by
   `scion-server ticket-key`, written 0600 into the server's data volume).
2. Builds the image and starts the two services.
3. Commits one file into repo `demo` and lands it on `main`.
4. Runs `scn checkout` against the cache (`--objects`), which verifies the
   ticket and fetches from the server, and diffs the result.

## Secrets are never committed and never in the image

Everything under `docker/demo/certs` is generated by `docker/demo.sh` on
your machine, and `.gitignore` keeps it out of the repository. The image
carries no keys, no certificates, and no tokens; every secret reaches a
container through a volume or an environment variable that the demo script
sets. `docker/demo/certs` holds a demo CA only: replace it with real
certificates and a real token for anything that matters.

## The pieces

- `Dockerfile` (repo root): multi-stage build, pinned to the MSRV image
  `rust:1.88-bookworm` (the same one the `check (MSRV)` CI job checks, so
  the image always builds with a supported toolchain). The runtime is
  `debian:bookworm-slim` with `ca-certificates`, running as the non-root
  user `scion` (uid 10001); data lives under `/data`, which a named volume
  owns.
- `docker/compose.yml`: the `server`, `cache`, and a one-shot `scn` runner.
- `docker/demo.sh`: the script the steps above describe.

## CI

The `docker` job in `.github/workflows/ci.yml` runs the same script on
every push, so the image and the demo cannot rot.
