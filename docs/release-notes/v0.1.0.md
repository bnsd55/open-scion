# v0.1.0 — release notes

The first release of Scion: a version control server that stores its
history as content-addressed objects in SQLite or Postgres, cache tiers
in front of it, and `scn`, a client that lands changes from many agents
at once and checks out sparse trees through the tiers.

A reader takes the release two ways: the source at the tag (the
README's quick start builds and runs it), or the release's artifacts —
the four binaries (scion-server, scion-cache, scion-daemon, scn), the
source tarball, and a CycloneDX SBOM per shipped binary's crate, each
with a GitHub artifact attestation and a checksum. Windows is not
supported. The release ships Linux x64 and macOS arm64 binaries;
linux-aarch64 returns with v0.8
([ROADMAP.md](../ROADMAP.md)). The supported platforms are the ones
the matrix names: Ubuntu 24.04 x86-64 and macOS 15 arm64, Postgres 17.11
([support.md](../support.md)). SQLite is the alpha backend — the one
every measured number below ran on. Postgres is experimental in v0.1.0:
tested in CI; not yet recommended for production or relied on for
data-safety evidence.

## What is proven

Every claim below is a gate that ran on the released commit; the check
names where to look.

- The whole CI suite: build, clippy (twice: with and without the
  test-hooks feature), fmt, rustdoc, cargo-deny (advisories), the unit
  and integration suites on Linux, the same on macOS, Postgres 17.11
  natively, the power-loss drill (LazyFS fault injection), an NFS mount
  run, gRPC conformance from a non-Rust client, a fuzz smoke, the MSRV
  build, the Docker demo, and the scorecard policy.
- The README's quick start walks end to end on every supported
  platform, from a clean build, once under umask 022 and once under
  002, in the release-smoke job.
- A restore of a stated store passes `fsck` and serves
  (crates/scion-server/tests/backup.rs); the durability point is
  documented in [operations.md](../operations.md) §3.
- Secrets (bearer tokens, TLS keys, ticket keys) are read through one
  checked descriptor: ancestor directories, symlink refusal, owner, and
  mode on the open file; POSIX ACLs on top. The release notes of the
  security section of the changelog carry the details.
- The release artifacts are built twice, from the signed tag, on
  separate runners, and the two builds agree byte for byte before
  anything is published; each artifact carries an attestation the
  reader verifies with
  `gh attestation verify <file> --repo bnsd55/openscion`
  ([slsa.md](../slsa.md)).

The 72-hour soak (Run A) ran 66 h 40 min on `5f0e428f` and was accepted
as a partial run ([#399](https://github.com/bnsd55/openscion/issues/399));
it is not evidence for this tag.

## Measured numbers

With the runs they came from; the scripts that make them are in
`scripts/` and the method is in [benchmarks.md](../benchmarks.md).

### Sparse checkout, 50 jobs at once

From one `bench.yml` run
([run 39306408455](https://github.com/bnsd55/openscion/actions/runs/39306408455),
`main` at `7b7789f`, `ubuntu-24.04`, tokio at `tokio-1.53.0`, 5
repetitions per state, medians):

- A cold checkout of `tokio/src/` (377 files, 3.3 MiB) through a fresh
  daemon: 1.50 s wall, 0.09 server CPU s, 0.91 MiB sent.
- git clone of the same files: 33.15 s wall, 799.89 MiB of pack —
  22.1x slower, 879x more bytes.
- git clone --filter=blob:none: 13.96 s — 9.3x slower.
- The warm daemon: 1.35 s; git's mirror clone 0.80 s — the one place
  git is faster (1.7x), on local object reuse where nothing moves over
  the wire.

The full tables, with CPU and bytes and what the numbers do not
measure, are in [benchmarks.md](../benchmarks.md).

### Restore

From the `restore-bench` workflow
([run 39529777685](https://github.com/bnsd55/openscion/actions/runs/39529777685),
the stated store: 20 repos, 1000 changesets, about 32 MiB of raw blob
content in files of about 32 KiB, on the fixed `ubuntu-24.04` runner):

- restore 0.0 s (build 0.5 s), against the 600 s bound the workflow
  enforces. The store is small; the number is the drill's, not a
  promise, and the workflow reprints it on every run.

### Capacity envelope

Not measured in v0.1.0. The first grid run showed the harness measuring
the wrong thing (the reader axis, the failure counters, the throughput
and the store-growth columns); the fixes land first, then the envelope
is measured on a clean run and published (#387).

## What this release does not have

- No crates.io publish: the crates carry the metadata for a later
  publish, decided against until a real outside consumer exists (D12).
- No failover, no multi-server story: one server per store
  ([ROADMAP.md](../ROADMAP.md) D11).
- The compat window, the N-1 support split, and the second operator
  drill are v0.4 and v0.8 gates, not this release's.

## Upgrading

Nothing to upgrade from: the first release. The schemas the release
writes are documented in [stability.md](../stability.md); a patch
release of v0.1.x may change them only as that document allows.
